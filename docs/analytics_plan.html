What we want to know

Analytics earns its place by answering questions that change the game. These are the ones 88fits has, in the order they will matter.

Is it fun enough to come back to?

Day 1, day 7 and day 30 retention; session length; runs per session; how many players ever finish a stage. The number every decision hangs on.

Where does the difficulty curve break?

Deaths by minute and stage, what killed the hero, the hero's level and build at death, how many reach the Gila, the Brander, endless. Stage 2 is meant to be a wall, not a cliff; this says which.

Which builds win, which never get picked?

Pick rate against extract rate for every weapon, path, line, passive and perk; rerolls and banishes by item (a banish is a vote); the level-up decision time.

Does the meta pull?

Gold banked against gold spent on the Upgrade board, which talents and forms, how many runs between purchases, whether players extract early to bank or push for the boss chest.

Does it run on their phones?

Frame time by device model and stage, the worst frames, memory, load time, thermal throttling in endless, script errors in the field with the breadcrumb that led to them.

Does anyone read the hints?

Which first-play hints show, whether the joystick is found in the first ten seconds, how often the pause strip is tapped by mistake, whether the top inset is right on notched phones.

The tool: PostHog, through its HTTP API

Three candidates were weighed against what a one-person Godot project on Android can actually run. The choice is PostHog Cloud (EU region): a hosted event store with funnels, retention, trends, session properties and a SQL layer, a free tier of one million events a month, and a plain HTTPS batch endpoint that Godot's HTTPRequest talks to in forty lines. No SDK to port, no Android plugin to rebuild for every Godot release, and if the free tier is ever outgrown the same client points at a self-hosted PostHog on the art server.

PostHog Cloud chosen

  • How Godot talks to it: POST https://eu.i.posthog.com/batch/ with a JSON body of events and the project's public key. No signing, no SDK.
  • Free tier: 1M events a month, 1 year of history; at ~40 events a run that is 25,000 runs a month before a bill.
  • What it gives back: funnels, retention tables, trends with breakdowns by any property, cohorts, dashboards, and HogQL (SQL) for anything else, all in the browser and readable on a phone.
  • Risk: a general product tool, so game-shaped views (a death heatmap) are built from properties, not offered ready-made.

GameAnalytics runner-up

  • Made for games: progression, resource and design events, funnels per level, free with no event cap.
  • No Godot 4 SDK; the REST collector needs an HMAC signature over the body and a server-time handshake, which is doable but every event must fit its five fixed shapes.
  • Property breakdowns are weaker: a death broken down by weapon, level and killer at once is not a view it offers.

Firebase Analytics passed over

  • Free and unlimited, with the Play Store's crash reporting next door.
  • Needs a native Android plugin compiled against the Godot version in use; the community plugins lag each release and the export pipeline is already fragile enough (JDK, templates, keystore).
  • Event shapes are capped (25 properties, 500 event names) and the console lags a day; fine later, wrong for the first month of tuning.

Own server later, maybe

  • A Postgres table and a script on the art server would hold the same JSON; the client is written so the endpoint is a setting.
  • Everything else (dashboards, retention maths, uptime) would be ours to build. Not before there are players.

The Godot client

One autoload, Analytics, beside Save and Run. Every other script calls Analytics.track("run_end", {...}) and nothing else; the autoload owns identity, batching, the queue on disk and the network.

Identity
A random UUID made on first launch and kept in the save file (install_id). It is the PostHog distinct_id. No account, no advertising id, no device serial. Wiping the save makes a new one.
Session
A new session_id when the app opens or comes back after five minutes in the background; every event carries it, so runs and menu time group under it.
Super properties
Stamped on every event: app version, Godot version, OS and version, device model, screen size and the top inset, language, and during a run the hero, map, stage and run id. Set once, changed when the run changes.
Queue
Events go into an array and to user://analytics_queue.json on every change past twenty events, so a crash or a killed process loses at most a handful. On launch the file is sent first.
Flush
Every 30 s, at 20 queued events, on run_end, when the app pauses (Android's NOTIFICATION_APPLICATION_PAUSED) and on quit. One HTTPRequest in flight at a time; a failure keeps the batch and retries with backoff (30 s, 60 s, 5 min), so a phone with no signal on the bus sends everything at home.
Rate
High-frequency things are sampled, never streamed: a perf_sample every 15 s of play, a damage summary per stage instead of a hit event per hit.
Off switch
Settings.analytics, on by default after the consent line, a switch in Settings under Sound and Music. Off means track() returns at once and the queue file is deleted.
Schema
Every event carries schema: 1. A field's meaning never changes; a change is a new field or a new schema number, so old dashboards keep reading.
Debug
The developer menu shows the queue length, the last send's status, and a switch that routes events to a separate PostHog project so Garry's test runs never pollute the players' numbers.

The autoload, sketched

## core/autoload/Analytics.gd
extends Node

const ENDPOINT := "https://eu.i.posthog.com/batch/"
const KEY := "phc_..."            # the project's public key (safe to ship)
const FLUSH_EVERY := 30.0
const FLUSH_AT := 20

var _queue: Array = []
var _http: HTTPRequest
var _timer := 0.0
var _backoff := 0.0
var _super: Dictionary = {}

func _ready() -> void:
    _http = HTTPRequest.new()
    add_child(_http)
    _http.request_completed.connect(_on_done)
    _super = {"app_version": ProjectSettings.get_setting("application/config/version"),
        "os": OS.get_name(), "os_version": OS.get_version(), "device": OS.get_model_name(),
        "screen": "%dx%d" % [DisplayServer.screen_get_size().x, DisplayServer.screen_get_size().y],
        "top_inset": W.safe_top(), "lang": OS.get_locale_language(), "schema": 1}
    _load_queue()

func set_run(props: Dictionary) -> void:     # hero, map, stage, run_id; {} when no run
    for k in ["hero", "map", "stage", "run_id"]:
        _super.erase(k)
    _super.merge(props)

func track(event: String, props: Dictionary = {}) -> void:
    if not Settings.analytics:
        return
    var p := _super.duplicate()
    p.merge(props, true)
    p["session_id"] = Save.session_id()
    _queue.append({"event": event, "distinct_id": Save.install_id(), "timestamp": Time.get_datetime_string_from_system(true), "properties": p})
    if _queue.size() >= FLUSH_AT:
        flush()
    elif _queue.size() % 5 == 0:
        _save_queue()

func flush() -> void:
    if _queue.is_empty() or _http.get_http_client_status() != HTTPClient.STATUS_DISCONNECTED or _backoff > 0.0:
        return
    var body := JSON.stringify({"api_key": KEY, "batch": _queue})
    _http.request(ENDPOINT, ["Content-Type: application/json"], HTTPClient.METHOD_POST, body)

func _on_done(_r: int, code: int, _h: PackedStringArray, _b: PackedByteArray) -> void:
    if code == 200:
        _queue.clear()
        _save_queue()
        _backoff = 0.0
    else:
        _backoff = 30.0 if _backoff == 0.0 else minf(_backoff * 2.0, 300.0)

func _process(delta: float) -> void:
    _timer += delta
    _backoff = maxf(_backoff - delta, 0.0)
    if _timer >= FLUSH_EVERY:
        _timer = 0.0
        flush()

func _notification(what: int) -> void:
    if what == NOTIFICATION_APPLICATION_PAUSED or what == NOTIFICATION_WM_CLOSE_REQUEST:
        _save_queue()
        flush()

The hooks are all in places the code already has: Game._start_run, _on_level_up, CardPool.apply, _on_boss_died, _on_portal_decided, _on_player_died, _on_revive_decided, end_run, Save.buy_talent, Settings.set_value, the breadcrumb ticker and Perf.report(). Each becomes one Analytics.track line.

Setting up PostHog, step by step

What you do at the PostHog end and at the game end, in order. Nothing here needs a credit card: the free plan carries a million events a month, and a run sends about two hundred, so the first five thousand runs a month cost nothing. Budget half an hour for steps 1 to 6; the dashboards in step 8 are an evening.

  1. Make the account on the EU cloud. Go to eu.posthog.com/signup (the EU address, not app.posthog.com: the data then lives in Frankfurt, which keeps the GDPR story short). Sign up with the Google account, name the organisation 88fits. Skip the onboarding wizard's "install a snippet" page: there is no website to put it in.
  2. Make the project. One project, 88fits Android. In Settings → Project switch Autocapture off (it is for web pages) and leave Session replay off. Under Person profiles pick identified only: the game never identifies anyone, so no person profiles get created and the bill stays at events only.
  3. Copy the two strings the game needs. Settings → Project → Project API key: a key that starts with phc_. It is a write-only key (it can send events, never read them), which is why every mobile app ships one inside the binary. The host is https://eu.i.posthog.com.
  4. Give them to the game. Put both into game/content/analytics/analytics.json (the file the Analytics autoload reads; the plan's client section shows it): 
    { "host": "https://eu.i.posthog.com", "key": "phc_…", "enabled": true }
    Commit it: the key is public by design. A build with "enabled": false sends nothing, which is how the arena and the capture tools stay out of the numbers.
  5. Ship a build and watch it arrive. Install the APK, open the game, play a minute. In PostHog open Activity → Live events: app_open, run_start, level_up should appear within a few seconds of each other, with the properties the catalogue above lists. If nothing comes: the phone is on a network that blocks the host (try mobile data), the key has a typo, or the breadcrumb file in Settings shows the queue file growing (the client stores and retries, so the events come later).
  6. Name the properties once. Data management → Properties: mark hero, stage, killed_by, weapon, device_model as the ones you will group by; PostHog then offers them first in every insight. Mark run_seconds and frame_ms_p95 as numeric.
  7. Define the three actions the dashboards lean on. Data management → Actions: Played a run = run_end; Extracted = run_end where outcome = extracted; Died = player_died. Retention and funnels are built from these, so a renamed event later is a one-line fix here instead of twelve dashboards.
  8. Build the boards. Six dashboards as described in the previous section, plus the pulse board below. Each insight is a few clicks: New insight → Trends / Funnel / Retention, pick the action, group by the property, save to the dashboard. Set each dashboard's date range in its own header so the whole board moves together.
  9. Turn on the one alert that matters. On the retention board, Subscribe to a daily email of Day-1 retention and of script_error counts. The first tells you if a build hurt the game, the second if it broke it, without opening the site.
  10. Say so in the store listing. The Play Console's Data safety form: analytics, device identifiers, app activity; collected, not shared; encrypted in transit; the in-game switch lets the player turn it off. The privacy page the listing links to names PostHog and the EU region.
What not to do. Do not add the PostHog Android SDK: the game is Godot, and the plain HTTP batch endpoint the autoload uses is the same thing with none of the Gradle work. Do not identify players (no identify calls, no emails, no names): the device id is the whole identity. Do not send the save file or the breadcrumb: both are the player's.

The pulse: what is happening right now

The dashboards above answer questions over days. This board answers one question in a glance: is anyone playing right now, and how is it going for them. Every tile looks at the last fifteen minutes or the last hour, the board refreshes itself every minute (dashboard settings → auto refresh), and nothing on it needs a date picker. It is the board to leave open on a second screen the week the game goes out.

What the board will look like

A few more pulse numbers worth a tile later

  • Revive ad acceptance, last hour: revive_decided where choice = ad over all player_died; the number the ad revenue stands on.
  • Level-up decision time, live: the median seconds between a level_up and the next card pick, from the runs in progress; a jump means a confusing new card.
  • Builds in the field: players by app version in the last hour, so a rollout can be watched taking over.
  • Slow frames per run, live: slow_frame counts for the runs in progress, grouped by device model; the first warning of a build that drops frames.
  • Hints shown to new players, last hour: which first-play hints fire and whether the joystick is found inside ten seconds (hint_shown and the first move).
  • Portal choices, last hour: continue against extract at each portal, and Stay at the last one; the live read of how far people dare to go.

Privacy and consent

Nothing collected identifies a person: a random install id, a device model, an OS version, a language and what happened in a game. No location, no contacts, no advertising id, no account. That still counts as personal data under the GDPR where it is combined with an install id, so the rules are short and kept:

  • Say so once. A one-line card on first launch: "88fits sends anonymous play statistics (what you picked, where you died, how the phone kept up) to help tune the game. No account, no location. You can turn it off in Settings." Two buttons, both proceed. Recorded as consent.
  • An off switch in Settings, next to Sound and Music, that stops sending and deletes the queue file at once.
  • Wipe the save, wipe the id. The install id lives in the save file the wipe already clears; a new id means a new anonymous player.
  • EU region. The PostHog project is created in the EU cloud so the data stays there; the endpoint above is the EU one.
  • Keep it lean. No free-text fields from the player, no screenshots, the error message capped at 200 characters and hashed for grouping. The Play Store's data-safety form will list "app interactions and performance, anonymous, optional".

Rollout

  1. Client and consent (one pass). The Analytics autoload, the queue file, the consent card, the Settings switch, the developer menu's queue readout and the test-project routing. Shipped with no events but app_open and consent, and checked from the phone against the PostHog live view.
  2. The run's spine. run_start, level_up, boss_started / boss_killed, stage_cleared, player_died, run_end. Boards 2 and 3 built. This is the pass that starts answering the difficulty question.
  3. The rest of the catalogue. Chests, paths, structures, pickups, the meta, hints, pause. Boards 1 and 4.
  4. Performance and errors. perf_sample from Perf.report(), slow_frame, script_error from a logger hook, unclean_exit from the breadcrumb. Board 5 and 6.
  5. Read it monthly, act on it per pass. Each balance pass opens with the death heatmap and the pick-against-win chart for the last build, and its CLAUDE.md paragraph records which number it was answering.
Cost and effort. PostHog's free tier covers the numbers above until there are tens of thousands of runs a month. The client is a day of work; the events are a line each at hooks the code already has; the six boards are an afternoon in PostHog's UI. The consent card and the data-safety form are the only parts that touch the store.

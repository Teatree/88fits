What changed since the first plan, and why

The first plan (pass 43, setup added in pass 44) still picked the right tool. Most of what sits around the tool has moved on, because the game moved on. Twelve passes later, this is what I would change, and what this version does.

One set of hooks, two destinations

Pass 45 built a run recorder (RunAnalytics) that already hears every moment of a run: each pick and its route, chests, skips and banishes, bosses, portals, the death and its last hits, and a sample every second. The old plan wanted a second set of hooks all over the game. Now the PostHog client listens to the recorder instead, so the local file and PostHog can never disagree.

The file you were looking for now exists

The old plan told you to paste the key into game/content/analytics/analytics.json. That file was part of the plan and was never built, which is why you could not find it. It now lives at game/config/analytics.json (outside content/, which the game scans for items), and the code that reads it is built.

Every run knows which Level Editor version it played

You tune the run in the Level Editor, often several times a day. Every event now carries map_rev, a short fingerprint of the map's timeline as the game loaded it. A board can then put "before my cap-curve change" beside "after it", which the old plan could not do.

Your local dashboard, for every phone

The charts you asked for in the local dashboard (power against pressure, the crowd against the cap, spawns and kills, health, damage per weapon, what hurt you) were all per second. Per-second rows from every phone would burn the free tier. Each run now sends one run_summary with the same curves per minute, so PostHog can draw the median player's version of your dashboard.

The catalogue follows the game as it is

No starter pick (every hero lands with a start weapon down the spawn beam), no selling at chests (skip, banish or take), three kinds of item (weapons to level 5, lines to level 4, passive items), skips and banishes per stage, mutation offers with the weapon reel, five heroes and their art looks, the Phoenix Feather, gold left in the sand on a death, the Upgrade board with six ranks.

Boards built around how you tune

The old six boards opened with retention. You are one player today, so retention can wait; what you do every day is pace the run and balance items. The boards now open with Level Editor versions and the run's curves, then deaths, builds, heroes and looks, the economy and performance. Retention joins when there are players.

Tag your own runs, do not hide them

The old plan routed test runs to a second project. With you as the only player that would leave the real project empty. Instead every event carries dev: true for runs from the editor binary or with debug mode on. The arena, the test runner and every tool never send at all.

The editor learns from real runs

The Level Editor's new "Spawned so far" row has to guess how fast the hero kills. It reads that from your recorded runs today, and later from the field. The plan now closes that loop instead of stopping at the dashboards.

Players, the phone and surveys

Your three requirements of 7 October and your answers: follow friends first, show the game's name for them in Settings, keep it through a wipe, read PostHog on the phone with no website of our own, questions only on the Results screen and no reward for answering. built in v0.45

The play-data card (the consent pop-up)

Yes, a pop-up: a small poster card over a dark dim on the title, the first time a build with a key starts. It reads:

A QUICK WORD · PLAY DATA
88fits sends what happens in your runs (the items you pick, where you fall, how smoothly it runs) to its maker, to make the game better. You are "Sly Outlaw 52" there: no account, no location, nothing else about you. Now and then it asks two or three quick questions after a run. You can turn either off in Settings.
[ NO THANKS ] [ OK ]

  • Until it is answered nothing leaves the phone and nothing is written to disk; the events of that first launch wait in memory.
  • OK turns play data on, sends what waited with a consent event, and fetches the surveys. No thanks turns play data off and deletes what waited; nothing is sent, ever, until the player turns the switch on in Settings (which records a yes).
  • A tap on the dim does nothing: the card wants an answer. The back gesture leaves it unanswered and it comes again next launch.
  • The answer is kept in the save and survives a wipe. Your own phone sees it once too, the first launch of v0.45.

One player, one name

  • Every install is a Person in PostHog (person profiles are on), under its random install id. The id survives a wipe, so a friend stays one person.
  • The game names them from the id: two western words and a number ("Dusty Coyote 41"). It is sent as the person property player_name and shown in Settings at the foot, next to the version ("88fits v0.45 · Dusty Coyote 41"), so a friend can read it out to you.
  • Find a friend: PostHog → People → search their player_name. Their page lists every session and event in order; a run's whole story is its run_end and run_summary.
  • Give them your name for them, once: People → Cohorts → New cohort → "Sasha" → match people whose player_name equals "Dusty Coyote 41" → Save. From then on every insight and board can filter or break down by that cohort, and the game never touches it. (If your PostHog shows an edit button on a person's properties, a label property works the same way: the game never writes label.)
  • The "One player" board: a dashboard whose filter is the cohort (or player_name): runs per day, a table of their run_end events (date, hero, result, minutes, level, kills, killer), their deaths by stage, and their survey answers.

Reading it on the phone

  • No website of ours: PostHog's own site in the phone's browser. Sign in once at eu.posthog.com, then Share → Add to Home screen on the pulse board for a one-tap icon.
  • Boards sized for a phone: one column, at most six tiles each, numbers before charts (a number tile reads at any width), single-line trends, tables of four columns at most. The wide tables (item pick rates) get their own board for the PC.
  • The morning email: open the pulse board → the ⋯ menu → Subscribe → email, daily, 8:00. Most days you read it in the mail app and open nothing.

Surveys after a run

  • Written in PostHog, drawn by the game. PostHog Surveys keeps the questions; the game fetches the running surveys when it starts (and keeps a copy for runs with no signal) and draws them itself on the Results screen in the Wanted style, one question a page: a row of numbers for a rating, buttons for choices, a text box for a written answer (optional ones can be left empty). PostHog receives its own events (survey shown, survey sent, survey dismissed), so the Surveys page shows the answers, the response rate and who said what.
  • When: only on the Results screen, after runs of a minute or more, at most once every three such runs, never twice in one session, and each survey only until that player answers it (the first long run of a new install can bring one). No reward for answering.
  • Opting out, visible to you: "Don't ask me again" under the card, or Settings → "Questions after a run". Either sends survey_opt_out (with where: card or settings) and sets the person property surveys_opt_out = true; switching back sends survey_opt_in.

The first survey, to create once in PostHog

Nothing shows until a survey is running in PostHog. Make this one (about three minutes):

  1. Surveys → New survey (blank, no template). Name it After a run · v1.
  2. Presentation: API. The game draws it; ignore the appearance and colours. Leave Display conditions, targeting and linked flags empty (the game asks everyone who has not answered).
  3. Question 1 · Rating: "How much fun was that run?" Display: number, scale 1 to 5, lower label "Not fun", upper label "Loved it". Not optional.
  4. Question 2 · Single choice: "What would make the next run better?" Choices: More weapons and items · More kinds of creatures · Harder · Easier · Something else. Not optional.
  5. Question 3 · Freeform text: "Anything else you'd tell me?" Description "A word is plenty." Optional.
  6. Save, then Launch. Phones pick it up the next time the game starts.

Editing the questions later

  • Small changes (a question's words, a description, a label, a choice's words, optional or not): open the survey → Edit → change → Save. Phones get the new words at their next start. Answers already given stay attached.
  • Adding or removing a question works the same way; the game shows whatever the survey holds (up to a handful of questions is kind to a thumb).
  • A new round of questions for everyone, including friends who already answered: stop the old survey (Stop), Duplicate it, change it, name it v2, Launch. The game asks each player each survey once, so a new survey is asked again.
  • Types the game draws: Rating (numbers 1 to 10; emoji display is drawn as numbers), Single choice, Multiple choice, Freeform text. A Link question is left out.
  • Pause all questions: stop every survey. Nothing in the game needs to change.

What we want to know

In the order they matter to you now.

Did my Level Editor change make the run harder or easier?

Deaths per minute, the extract rate, the level reached at the King and the Gila, split by map_rev. The question every editor save raises.

Is the pacing right, minute by minute?

The crowd against the cap, spawns against kills, the crowd's pressure against the build's power, the hero's lowest health: the median and the spread across runs, per minute of play.

Where, and to what, do heroes die?

Deaths by stage and minute, the killer, the last hits, the build at death. Stage 2 should be a wall, not a cliff.

Which items win, which are skipped?

Pick rate against extract rate for weapons, lines, passive items, mutations and evolutions; what gets skipped and banished (a banish is a vote); the chest's take, skip and banish.

Do the heroes and their looks pull?

Runs per hero and their extract rate; which art look players keep (Solenne's four walks); whether locked heroes get looked at.

Does the meta pull?

Gold earned, banked and left in the sand; Upgrade ranks bought and refunded; runs between purchases.

Does it run on their phones?

Frame rate by device and stage, the worst frames, and later script errors from the field.

Do they come back?

Day 1, 7 and 30 retention and session length. Waits for players; the events for it are sent from day one.

How the data flows

The Godot client, as built

One autoload, Analytics (game/core/autoload/Analytics.gd), beside Save and Run. It owns the key file, identity, the queue on disk and the network. The recorder hands it events; nothing else in the game calls it.

The key file

game/config/analytics.json
{
  "host": "https://eu.i.posthog.com",
  "key": "",            <- paste the phc_... Project API key here
  "enabled": false      <- set to true
}

An empty key, a key that is not a phc_ Project key (a personal phx_ key is a secret, and the client refuses it) or "enabled": false means nothing is queued and nothing is sent. The key is write-only (it can send events, never read them), which is why every mobile app ships one inside the binary; it is safe to commit.

Never sends
From headless runs (every tool and smoke run), the test runner, the debug arena, or with the Settings switch off.
Your runs
Runs from the editor binary or with debug mode on are sent with dev: true; filter dev = false once there are players.
Identity
A random install_id made once and kept in the save, through a wipe too (v0.45). Person profiles are on: each install is a Person named by the game (player_name, shown in Settings). A session_id per app open and after five minutes away. No account, no advertising id, and PostHog's IP location switched off on every event ($geoip_disable).
Consent
The play-data card on the first launch (v0.45, see Players, phone, surveys): nothing leaves until it is answered.
Labels on every event
schema 1, app_version, os, os_version, device, screen, top_inset, lang, dev; during a run also run_id, hero, hero_look, map, map_rev and stage.
Queue
In memory and in user://analytics_queue.json (saved every few events and when the app pauses), sent first on the next launch; at most 2000 kept, the oldest dropped.
Sending
A POST to {host}/batch/ every 30 s, at 20 queued events, at the run's end, when Android pauses the app and on quit. One request at a time; a failure keeps the batch and waits 30 s, then 60 s, up to 5 minutes, so a phone with no signal sends everything later.
Off switch
Settings, "Anonymous play data": off stops sending and deletes the queue at once.
Readout
The developer menu shows whether the key is set (never the key), whether sending is on, the queue length, how many events went this session, the last send's status and time, and a Send now button.

Setting up PostHog, step by step

What you do at the PostHog end and at the game end, in order. Nothing needs a card: the free plan carries a million events a month, and a run sends a few dozen. Budget half an hour for steps 1 to 6; the boards are an evening.

  1. Make the account on the EU cloud. Go to eu.posthog.com/signup (the EU address, so the data lives in Frankfurt). Name the organisation 88fits. Skip the wizard's "install a snippet" page: there is no website.
  2. Make the project. One project, 88fits Android. In Settings → Project switch Autocapture off and leave Session replay off. Under Person profiles leave them on (v0.45 makes a Person of every install so you can follow a friend; the free plan's million events a month still covers it). Before v0.45 this step said identified only, so the bill stays at events.
  3. Copy the key. Settings → Project → Project API key: it starts with phc_. The host is https://eu.i.posthog.com.
  4. Give it to the game. Open game/config/analytics.json, paste the key between the quotes after "key": and change "enabled": false to true: 
    { "host": "https://eu.i.posthog.com", "key": "phc_…", "enabled": true }
    Commit it: the key is public by design.
  5. Ship a build and check it from the phone. Run bash tools/ship.sh, install from Drive, play a minute. In the game, open the developer menu (hold the version line in Settings for two seconds): the Analytics lines should say the key is set, sending is on, and the last send was 200. In PostHog open Activity → Live events: app_open, run_start and level_up should arrive within seconds. If nothing comes: check the readout's last status (401 means the key is wrong), try mobile data, or tap Send now.
  6. Pin the properties you will group by. Data management → Properties: mark map_rev, hero, hero_look, stage, killed_by and dev, so PostHog offers them first in every insight.
  7. Define the actions the boards lean on. Data management → Actions: Played a run = run_end; Extracted = run_end where result = extract; Died = player_died. A renamed event later is then a one-line fix.
  8. Build the boards. Built by a script since v0.45: python tools/posthog_boards.py makes the nine dashboards (Pulse, Players, Level Editor versions, Run curves, Run health & weapons, Deaths, Builds & items, Surveys, Coins), one column each so they read on a phone. Since v0.46 a rerun keeps every board (its id and link stay) and replaces its tiles, so change a tile in the script, not in PostHog. The curves land each per-minute bucket on its end minute and scale per-bucket sums to a per-minute rate, so a long run folded into two- or four-minute buckets still draws right. It reads a personal API key (phx_, scopes dashboard / insight / cohort write and query read) from tools/posthog_personal_key.txt, which git ignores; --check runs every query and builds nothing.
  9. One alert. On board 1, subscribe to a daily email of runs and deaths by map_rev: it tells you how the last editor save played without opening the site.
  10. Create the first survey (see Surveys): PostHog → Surveys → New survey, presentation API, the three questions, Launch.
  11. Before the Play Store. The store's Data safety form (the consent card is built since v0.45) (analytics, app activity, device id; collected, not shared, encrypted in transit; the Settings switch turns it off). Not needed while you are the only player.

What not to do. Do not add the PostHog Android SDK (the game is Godot; the batch endpoint is the same thing with no Gradle work). Do not send the save file or the breadcrumb. Never paste a phx_ or phs_ key into the game: they are secrets; only the phc_ project key goes in.

The Level Editor loop

The editor's new Spawned so far row estimates every creature a run makes: regular, coloured, Elites, Specials and Bosses, under your caps and patterns. A run only spawns what the hero kills, so the estimate needs a kill rate. Today it reads that from your recorded runs on the PC (analytics/runs/): the share of the live crowd killed each second, and how long boss fights last. Once PostHog has runs, the same numbers per map_rev come from the field: one SQL insight over run_summary's m_killed and m_alive, exported as a small JSON the editor reads. Then the editor shows its estimate beside what real players saw on that version.

Privacy and consent

  • Nothing identifies a person by name: a random install id, a device model, an OS version, a language and what happened in a game. No location, no contacts, no advertising id, no account. Each install is a pseudonymous Person in PostHog under a made-up name, which is still personal data under EU rules: the play-data card asks first (built in v0.45).
  • Asked first, switchable after: the play-data card on the first launch; Settings → Anonymous play data stops sending and deletes the queue; Settings → Questions after a run stops the surveys.
  • One player through a wipe: a wipe takes the progress, not the player: the id, the name, the card's answer and the survey record stay (Garry: friends stay one person).
  • EU region: the project lives in PostHog's EU cloud.
  • Before the Play Store: a privacy page naming PostHog and the EU region, and the store's Data safety form.
